# 랜딩·사용자 요구 선택·맞춤 UI 분석

등록일: 2026-11-15 · 관련: REQ-COM-011

## 목적과 사용자 흐름

처음 방문하면 서비스 목적을 설명하는 랜딩 → 필요한 도움 선택 → 쉬운 첫 화면 또는 기존 노선도로 이동한다. 설정 없이도 로그인 없이 바로 이용할 수 있다. 재방문은 저장한 화면으로 시작한다.

추가 피드백 반영: 소개와 주요 동작을 랜딩 중앙에 배치하고, 설정은 같은 랜딩 안에서 펼쳐 완료한다. 앱 밖에 고정했던 두 버튼 바는 제거했다. 앱 진입 후에는 폰 콘텐츠 상단 중앙의 ‘내 화면 바꾸기’ 하나로 랜딩 설정에 돌아간다. 쉬운 첫 화면의 제목·과업 영역도 중앙에 모았다.

사용자 구분의 기준은 나이·진단명 대신 본인이 선택한 이용상의 필요다. 어르신도 작은 글씨만 불편할 수 있고, 젊은 사용자도 손 부상과 저시력이 겹칠 수 있다. 여러 선택을 함께 적용하며 특정 기능 이용을 제한하지 않는다.

이 문서의 사용자별 어려움은 설계 가설이다. 실제 참여자 조사나 접근성 인증을 완료했다는 의미가 아니다. W3C의 [고령 사용자 접근성 자료](https://www.w3.org/WAI/older-users/)와 [고령 사용자를 위한 설계 설명](https://www.w3.org/WAI/older-users/developing/)을 참고했다.

## 설정의 취합 방식

글자 크기와 대비·터치·움직임·쉬운 화면·계단 이용 도움을 하나의 Preferences로 합친다. 크기·대비·터치·움직임은 함께 적용한다. 쉬운 화면 또는 계단 이용 도움을 선택하면 첫 화면에 과업 버튼을 제공한다. 나이와 장애명은 입력받지 않는다.

설정은 `elevSubway.accessibility.v1`과 기존 글자 크기 저장소에 브라우저 단위로 저장한다. 맞춤 설정은 서버에 전송하지 않는다. 기존 앱의 역 조회·출발 계산·챗봇 API 사용과는 별개다. 저장을 지원하지 않는 환경에서도 이번 이용은 가능하다. 로그인 계정별 동기화·다중 이용자 분석·관리자 통계는 구현하지 않았다.

사용자가 말한 ‘사용자 취합’은 이번 구현에서 개인의 복수 요구를 조합하는 것으로 해석했다. 이용자 모집이나 통계가 목적이라면 별도의 대상·설문·저장 위치·수집 동의 설계가 필요하다.

## 디자인·접근성 기준

기존 파랑 브랜드 및 글자·간격 토큰을 재사용한다. 새 시작 버튼은 56px, 기존 앱의 큰 버튼 옵션은 최소 터치 토큰을 56px로 바꾼다. 이 값은 프로젝트의 사용 편의를 위한 선택이며 WCAG AA의 최소 요구값으로 표현하지 않는다. [W3C 표적 크기 설명](https://www.w3.org/WAI/WCAG22/Understanding/target-size-minimum)을 참고한다.

큰 글씨는 기존 100/112.5/125/150% 설정을 사용한다. 대비 옵션은 배경·본문·보조 문구·경계·브랜드 토큰을 변경한다. 지도 색상은 기존 노선 식별 체계를 유지한다. 전체 앱의 모든 요소가 특정 대비 비율을 충족한다고 인증하지 않는다.

## 검증

- `npm.cmd run build`: TypeScript 검사와 배포 빌드 통과.
- `npm.cmd test`: React·서비스 테스트 70개 통과.
- `node --test tests/*.test.cjs`: 기존 서비스 테스트 85개 통과(작업 전 기준).
- `node scripts/verify-welcome.mjs`: 개발용 mock 서버 5178 기준 Chromium 검증. 랜딩 진입, 최대 글씨에서 320/375/768/1440px 가로 넘침 없음, 설정 저장·재방문, 엘리베이터 기능 진입, 설정 취소 전후 질문 입력 보존, 지도 연결, 이전 Prototype-v2 초기화 확인. 외부 폰트를 차단해도 사용 가능한지 확인했다.
- 화면 증거: `web/artifacts/welcome/landing-desktop.png`, `settings-mobile-max.png`, `app-mobile-max.png` (Git 제외).

Chromium 자동화 및 화면 이미지 확인까지 수행했다. 실제 참여자 평가·화면낭독기 실기·Safari/iOS·현장 경로·실제 백엔드 통계는 검증하지 않았다.

기존 `test:browser`·`test:visual`은 첫 화면이 곧 노선도라는 이전 흐름을 전제로 하므로 이번 변경의 전체 회귀 결과로 인용하지 않는다. 새 진입 흐름은 위 `verify-welcome.mjs`로 검증했다. 이전 화면의 동등성 비교를 재실행할 때는 온보딩 완료 상태를 테스트 준비 단계에서 구성해야 한다.

## 후속 사용자 평가 제안

다음 단계는 그룹별로 사람을 모집해 ‘서비스 목적 설명하기 → 글씨 키우기 → 이용할 역 설비 찾기 → 출발 시각 확인하기 → 설정 되돌리기’를 수행하는 것이다. 성공 여부·도움 요청·오조작·완료 시간과 함께 피로도·불안감·안내 신뢰도를 기록한다. 전체 평균에 가려지지 않도록 요구 조합별 결과를 비교한다. 참여자 모집·개인정보 수집은 이번 변경에 포함하지 않았다.
